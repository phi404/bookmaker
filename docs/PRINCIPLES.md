# 実装と設計の判断原則

## 標準を先に成立させる

原稿を入れたら自然な紙面ができることを優先する。設定を追加する前に、標準値・自動処理・既存概念の組み合わせで問題を解けるか検討する。機能数や数値欄の多さを品質と見なさない。

初心者向けのプリセット、基本設定、詳しい数値の順で開示する。簡単に使えることと、設定できないことを同義にしない。

## 一つのBook Modelを複数のビューから編集する

原稿・構成・素材・GUI・設定は同じ本を扱う。原稿文字列や構成ビューを別の正本にしない。原稿の入力途中と確定済みのモデルを区別し、未完入力をGUI操作で黙って消さない。

原稿は文章として読める入力にする。内部がASTであることは、行番号・コード用書体・「ソース」という画面ラベルを要求する理由にならない。

## 本文の例外は意味で表す

改ページ、章の開始面、見出しと次段落の結び付け、段落のインデント、構造範囲の版面で扱う。本文の文字・行を手で数mm動かす機能は作らない。組版結果として座標を計算することは、この原則と矛盾しない。

スタイルを基本とし、局所変更は別に保存して解除できるようにする。対象・適用範囲・変更件数を見せる。変更を解除しても原稿文字や名前付きスタイルを壊さない。

## 構造と生成ページを混同しない

章のページ範囲は組版結果。章・ブロックの設定は安定IDへ結び付ける。ページ番号が変わっても意味的な範囲は同じ対象へ追従する。対象が消えたり同一内容で対応が曖昧になった場合は診断し、別の対象へ推測で付け替えない。

通しページへの固定指定は明示的な物理例外。意味的範囲へ勝手に変換しない。現在の容量を変えない例外と、将来の容量を変えるページ設定を分ける。

## 自由度は特殊ページの内側に隔離する

頻出するページは意味フィールドとテンプレート、足りない表現は自由ページ、外で完成したデザインは外部ページで扱う。自由ページの座標を本文やMarkdownへ広げない。特殊ページの表現方式を変えてもIDと構成位置を守る。

## 結果と作業の連続性を保つ

紙面を主役にし、原稿の入口と本文全体の設定へ戻る経路を維持する。選択しただけで設定やスマホの画面を乗っ取らない。変える意図を示した操作で対象の設定を開く。パネルの開閉や表示上の折返しで原稿を書き換えない。

同じ組版結果をプレビュー・PNG・PDFで共有する。書き出しは開始時のスナップショットを固定し、編集中の別revisionを混ぜない。

## 原稿と作業を保護する

取り込みはコピー。未知の文字や記法を黙って捨てず、未対応の構造は保存・警告・拒否を明示する。壊れた保存や未対応の作業ファイルを空のデータで上書きしない。移行前の原値を退避する。

未公開原稿を外へ送らない。実行時の外部フォント・分析・クラウド依存を勝手に追加しない。端末内保存と持ち出せる作業JSONを基本にする。

## 対応と合格を証拠で区別する

型があるだけの項目を対応済みとしない。未検査を合格と表示しない。文字保存・寸法・禁則を機械で、読みやすさと操作を目視でも確かめる。人間の利用者調査とAIのレビューも区別する。

不具合は再現fixtureと修正前の失敗へ変える。テストの無条件成功・skip・閾値緩和・基準画像の一括更新で回避しない。詳しい手順は [HARNESS](HARNESS.md)。

## 新しいケースを追加するとき

表現ケース → 既存の文字/段落/見出し/版面/章/範囲 → テンプレート/自由/外部の判断 → 反例fixture → 実装と検証、の順で進める。既存概念で表せない理由を [CASE_CATALOG](CASE_CATALOG.md) と [DECISIONS](DECISIONS.md) に残してから、新しい概念を足す。
